1. The Big Picture — How Audit AI Learns

Think of Audit AI like a new team member who needs to be trained. Except instead of shadowing one senior auditor for a year, it reads every finalized engagement HCLLP has completed over the past 15 years — across all framework types, all clients, all partners — and builds a mental model of how good audit work looks.

This training happens in three stages. Each stage builds on the one before it. Your role as the audit team is to prepare and label the source material so the system knows what it is reading and how much to trust it.

2. What the Audit Team Prepares — and Why It Is Not Just "Exporting Files"

Raw workpaper files alone are not enough. The AI system converts every workpaper into structured question-and-answer pairs before training. To do this correctly, it needs to know:

  • What kind of workpaper this is — is it a compliance test? A finding? A trial balance? Each type generates different kinds of training examples.
  • Which phase of the audit it came from — a planning document has different content patterns than a completion workpaper.
  • How time-sensitive its content is — a workpaper referencing specific dollar thresholds from 2012 should not be treated the same as one from 2024. But a workpaper explaining how to conduct a bank reconciliation test is just as valid in 2012 as it is today.

The audit team provides this information through a simple labeling file — one per engagement — called engagement_labels.csv. Every engagement folder submitted to the system must include this file.

⚠ Labels must be complete before training pairs are built

Before the system generates training questions from a workpaper, it checks that every workpaper in the engagement has a workpaper_type label. If any workpaper is missing its label, the training pair build step is blocked for the entire engagement and the system flags the engagement for re-submission.

What this means for you: Make sure engagement_labels.csv has one complete row for every workpaper before placing the engagement folder in the intake directory. A folder with a partially filled label file will be extracted and indexed normally — but it will not contribute to model training until labels are complete.

You will receive a notification from the ML team if an engagement is blocked at this step.

2.2 Understanding time_sensitivity — The Most Important Label

This is the label that most directly protects the model from learning outdated information. Here is how to think about it:

timeless — Methodology that does not expire

Use when: The workpaper is about how to do something — the objective of a test, how a finding should be structured, what independence requires. If you removed every dollar amount and every specific regulation citation from this workpaper, the remaining content would still teach a new auditor something valid today.

Effect: No age penalty. A 2009 timeless workpaper gets the exact same training weight as a 2024 one.

Examples: A narrative explaining the purpose of a bank reconciliation test. An audit program describing the steps in a risk assessment. An internal control narrative explaining how a control works — not whether it met a specific threshold.

time_static — Standard practice that ages slowly

Use when: The workpaper follows standard audit practice and would still be a reasonable reference, but some details — procedures, sampling approaches, regulatory language — may have been updated since. The approach is valid; you just would not cite it as your only source.

Effect: Gradual weight reduction based on age. Recent workpapers count more than old ones, but old ones still contribute meaningfully.

Examples: A compliance test documenting the procedure used to test a requirement — the procedure itself is still valid, even if minor guidance has changed. A risk assessment that identifies risks correctly but may not reference the latest risk assessment standard update.

time_sensitive — Threshold or regulation-version dependent

Use when: The workpaper directly references specific dollar amounts, audit thresholds, or regulation versions that have changed. If the model learned from this at full weight, it might generate outputs using outdated thresholds.

Effect: Aggressive age penalty. A time_sensitive workpaper from 2012 contributes almost nothing to training. A 2023 one contributes at reduced but meaningful weight.

Examples: A SEFA schedule (dollar amounts change every year). A compliance test explicitly citing the "$500,000 OMB A-133 threshold" (superseded — now $750,000 under 2 CFR 200). A materiality worksheet with specific calculated amounts.

Quick rule of thumb: If you removed all the numbers and regulation citations, is the methodology still useful? → timeless. Standard approach, no specific thresholds? → time_static. Has dollar amounts or regulation versions you know have changed? → time_sensitive.

By the end, they would understand how HCLLP writes findings, how we structure compliance tests, what a good management letter looks like, and how we document conclusions. They would not yet be an expert in any one framework — but they would speak the firm's language fluently. That is what Stage 1 does.

4. Stage 2 — Framework-Specific Training: Sharpening the Judgment

Analogy: After your new hire has read all 15 years of workpapers, you now sit them down with a specialist in each framework — one week with a Single Audit expert, one week with a GAGAS expert, and so on. By the end, they can not only write in HCLLP's style — they can apply the precise judgment each framework requires, without mixing them up. That is what Stage 2 does.

4.1 What Goes In

Stage 2 does not require new workpaper exports. It uses the same training pairs that were already generated in Stage 1 — but this time, it runs a separate focused training session for each framework type:

TrackTraining data usedWhat the model sharpens
Track A — Single Audit All Single Audit pairs from Stage 1 2 CFR 200 citation precision, SEFA structure, federal cluster compliance logic, $750K threshold application, questioned costs documentation
Track B — GAGAS All GAGAS pairs from Stage 1 Yellow Book independence language, performance audit reporting format, distinguishing financial from performance audit findings
Track C — GAAS All GAAS pairs from Stage 1 AU-C cross-references, private-sector risk and materiality language, going concern assessment, management representation requirements

Each track continues from the Stage 1 model checkpoint — it does not restart from scratch. This is the key design choice that prevents the model from forgetting what it learned in Stage 1 when it focuses on one framework.

4.2 How the Three Tracks Relate to Inference

After Stage 2, there are three framework-specific model versions. When an auditor uses Audit AI in the live system and selects their engagement, the system automatically loads the correct model version for that engagement type:

The gate ensures that only a framework that has passed a blind senior auditor review at ≥ 80% approval is made available for live use. Single Audit goes first because it has the largest, most recent training corpus.

4.3 Audit Team Action for Stage 2

Minimal action required from the audit team at this stage:

  • Confirm with the project team that your Stage 1 submission covered all framework types completely — particularly GAGAS and GAAS engagements
  • If any framework was under-represented in Stage 1 (e.g., fewer than 20 finalized GAAS engagements), provide supplemental exports with labels at this point
  • Participate in the blind review after Stage 2 is complete: senior auditors and partners review 250 AI outputs and rate them — this is what determines the 80% gate

5. Stage 3 — Targeted Refinement: Fixing What the Review Finds

What triggers Stage 3: After the blind review of Stage 2 outputs, the project team identifies patterns in what the model gets wrong. For example: it may consistently write vague management letter recommendations, or it may misclassify a particular type of finding. Stage 3 is a focused re-training session using only the highest-quality workpapers that demonstrate correct handling of those exact issues.

5.1 What Goes In

Stage 3 uses the partner-nominated gold-standard workpapers — the 50–100 engagements identified as HCLLP's best work — filtered to pairs with the highest quality scores and refined against the specific weaknesses found in the Stage 2 review.

No new exports are required. These workpapers are already in the system from the original Stage 1 intake. Partners nominated them by flagging their best engagements during the initial data preparation phase.

5.2 Audit Team Action for Stage 3

  • Partners: ensure your best-work nominations were submitted during Stage 1 intake (see Data Preparation Guide Section 3.3)
  • Senior auditors: participate in the targeted review session after Stage 3 runs — the project team will provide a focused set of 50 outputs covering the specific weakness areas

6. The RAG Knowledge Base — How Audit AI Searches Your Past Work at Query Time

The three training stages teach Audit AI how to do audit work. The RAG Knowledge Base teaches it what HCLLP has done before — and makes that institutional knowledge available every time an auditor asks a question.

RAG stands for Retrieval-Augmented Generation. The idea is simple: instead of relying only on what the model was trained on, every time an auditor makes a request, the system first searches the knowledge base for the most relevant past workpaper examples and includes them in the answer it generates.

Analogy: Imagine before answering any audit question, you had the ability to instantly search through every workpaper the firm has ever prepared, pull out the 5 most relevant ones, and read them before drafting your response. That is exactly what Audit AI does — in under a second.

6.1 How the Knowledge Base Is Built

The knowledge base is built automatically from the same workpapers the audit team submits for training. No separate action is required. As the ETL pipeline processes each workpaper, it also:

  1. Converts every workpaper section into a mathematical fingerprint (called a vector embedding — a list of 4,096 numbers that captures the meaning and context of the text)
  2. Stores that fingerprint in the Qdrant vector database alongside the original text
  3. For gold-standard validated findings, also stores them in a separate Validated Findings collection for consistency checks

The result is a searchable library of every workpaper section the firm has ever produced, indexed not by keyword but by meaning. Searching for "questioned costs finding in a CDBG program" will surface relevant workpaper sections even if they use different wording.

6.2 How Audit AI Uses the Knowledge Base at Inference Time

This is the full flow from the moment an auditor uploads a workpaper and asks a question to the moment the AI-assisted draft appears on screen:

Step 1 — Auditor Input

The auditor selects an engagement, uploads a workpaper (or selects one already in the system), and triggers an analysis — for example: "Document the finding for this compliance exception."

The workpaper goes through the same extraction and cleaning pipeline as the training data. It is split into sections. Each section is converted into a mathematical fingerprint using the same embedding model used to index the knowledge base.

Step 2 — Knowledge Base Search

The system takes the fingerprint of the current workpaper section and searches the Qdrant knowledge base for the 20 most mathematically similar past workpaper sections across all finalized engagements in the firm's history.

The search is filtered by:

  • Framework type — a Single Audit question only searches Single Audit past work
  • Recency — more recent workpapers are ranked slightly higher than older ones
  • PII scrubbed — only workpapers that have been fully anonymized are returned

The result is a list of 20 candidate past workpaper sections that are contextually similar to the current question.

Step 3 — Reranking (Selecting the Best)

The 20 candidates are passed through a reranker — a second AI model that reads each candidate alongside the current workpaper section and scores how genuinely relevant it is (not just mathematically similar, but contextually relevant to this specific question).

The top 5 highest-scoring candidates are selected. These become the retrieved context.

Step 4 — Consistency Check (Validated Findings)

Separately, the system also searches the Validated Findings collection — which contains only findings that have been reviewed and approved by a senior auditor or partner. It retrieves the 3 most similar past approved findings.

These are used to ensure the new output is consistent with how HCLLP has documented similar situations in the past. If the firm always phrases a particular type of recommendation a certain way, the model will see that pattern and follow it.

Step 5 — Context Assembly and Generation

The model receives a carefully assembled prompt containing six components:

  1. System context: Client type (NPO or Govt), GAGAS applicability, Single Audit flag, fiscal year
  2. Retrieved context: The 5 most relevant past workpaper sections (from Step 3), anonymized
  3. Consistency context: The 3 most similar past approved findings (from Step 4)
  4. Computed audit facts: Pre-calculated figures from the Audit Calculation Engine (see Section 7) — materiality, reconciliation totals, threshold breach results, variances. The model is explicitly told "do not recalculate — these figures are Python-verified."
  5. Current workpaper: The section the auditor is asking about
  6. Task instruction: What the auditor has asked for (finding documentation, risk classification, etc.)

The model generates its response with all of this in its "working memory" — the context window. Critically, all arithmetic is done before the model sees the workpaper. The model reads verified numbers and writes the analysis — it does not compute anything itself.

Step 6 — Validation and Output

Before the result reaches the auditor, an automated validator checks:

  • Every regulation citation against the master regulations list — any unrecognized citation is flagged
  • Every dollar threshold against the current year's threshold file — any mismatch is flagged
  • The output for any language that resembles a signed audit opinion — these are blocked
  • All required fields are present — if any are missing, one retry is attempted

The final output is presented to the auditor labeled: "AI-Assisted Draft — Requires Senior Auditor Review Before Use." The auditor can see which past workpaper sections were used as reference (the retrieved context), can approve the output, edit it, or reject it entirely.

7. The Audit Calculation Engine — Why the AI Never Does the Arithmetic

The short version: Before the AI model sees any workpaper, a separate Python calculation engine runs first and computes all the numbers — reconciliation totals, materiality figures, threshold comparisons, variances. The AI then reads those pre-verified facts and writes the analysis. It never adds up columns or checks whether a number exceeds a threshold itself.

This is a deliberate design choice, not a limitation. AI language models are excellent at reading, interpreting, and writing — but they can make small arithmetic errors that would be unacceptable in an audit context. A reconciliation difference of $4,668 reported as $4,670 is an audit error. So all arithmetic is done by deterministic Python code — the same way a spreadsheet formula works — and the results are handed to the model as verified facts.

Analogy: Think of it like a senior auditor handing their staff a completed trial balance reconciliation worksheet and saying: "Here are the verified figures — now document the analysis and write the finding." The staff member does not re-add all the columns; they interpret the numbers and write the conclusion. That is exactly how Audit AI works: the Calculation Engine is the verified worksheet; the AI model is the staff member writing the analysis.

7.1 What the Calculation Engine Computes

The engine has six tools, each covering one type of audit computation. The system automatically selects which tools to run based on the workpaper_type label you assigned in engagement_labels.csv:

ToolWorkpaper types that trigger itWhat it computes
Threshold Checker All types Compares expenditure totals against regulatory thresholds (e.g. $750,000 Single Audit threshold under 2 CFR 200; Yellow Book and GAAS materiality benchmarks). Returns: threshold name, limit, your value, and whether it is breached — as a verified fact.
Materiality Calculator All types Computes planning materiality, performance materiality, and clearly trivial threshold using the engagement's total assets, total revenue, or total federal expenditures — depending on engagement type and framework. Returns all three tiers as verified figures.
Bank Reconciliation bank_reconciliation Reads the structured rows of a bank reconciliation workpaper and computes: outstanding checks total, deposits in transit total, adjusted bank balance, comparison to book balance, and unreconciled difference. Flags if difference exceeds tolerance.
Trial Balance Checker trial_balance Reads debit and credit columns row by row, sums each, verifies they are equal, computes any out-of-balance amount, and checks that subtotal rows match their source rows (catches spreadsheet formula errors that may not be obvious on screen).
Financial Ratios financial_statements, analytical_procedure Computes current ratio, quick ratio, debt-to-equity ratio, and days sales outstanding from the balance sheet and income statement rows. These ratios are then available to the model as verified facts for the analytical narrative.
Variance Analysis analytical_procedure, trial_balance, financial_statements Computes absolute and percentage variance for each line item between current and prior period. Automatically flags any item where variance exceeds 10% or performance materiality — so the model can focus its narrative on the right items without guessing at significance.

7.3 What the AI Actually Sees

Before generating any output, the AI model receives a section that looks like this — the pre-verified numbers, labeled clearly:

COMPUTED AUDIT FACTS (Python-verified — do not recalculate) Materiality (Single Audit — 2026): Planning materiality: $47,250 (0.5% of total federal expenditures: $9,450,000) Performance materiality: $23,625 (50% of planning) Clearly trivial: $2,363 (5% of planning) Bank Reconciliation: Balance per bank statement: $1,847,234.00 Less: Outstanding checks: ($14,822.50) Add: Deposits in transit: $19,444.00 Adjusted bank balance: $1,851,855.50 Balance per books: $1,851,902.00 Unreconciled difference: $46.50 ← WITHIN tolerance ($500) ✓ Threshold Check (2 CFR 200): Total federal expenditures: $9,450,000 → EXCEEDS Single Audit threshold ($750,000) Type A threshold (3%): $283,500 Single Audit required: YES

The model reads these verified figures and writes: "The bank reconciliation indicates an unreconciled difference of $46.50, which is within the firm's $500 tolerance threshold. No finding is required. Total federal expenditures of $9,450,000 exceed the Single Audit threshold..."

It did not compute those numbers. The Python engine did. The model explained them.

7.4 What This Means for the Audit Team — Numeric Workpapers

For the Calculation Engine to work correctly on workpaper content (bank reconciliations, trial balances, financial statements), the ETL pipeline needs to extract the structured row data — not just the text — from those Excel sheets. This happens automatically when you label a workpaper correctly:

If you label a workpaper as bank_reconciliation, trial_balance, financial_statements, or analytical_procedure in engagement_labels.csv, the system automatically extracts the numeric row structure from that workpaper and makes it available to the Calculation Engine. No additional action is required. The label is the trigger.

If an Excel workpaper cannot be read in structured form (e.g. it is a scanned PDF or the formatting is unusual), the system logs a warning and falls back to text-only processing — the AI still generates output, but without pre-verified computed figures. The output will carry a note to the auditor that the calculation engine did not run for this section.

7.5 Audit Team Action for the Calculation Engine

  • Label bank reconciliation, trial balance, financial statement, and analytical procedure workpapers with the correct workpaper_type in engagement_labels.csv — this is the only step required from your side
  • Ensure these workpapers are exported as Excel (.xlsx) from Caseware — scanned PDFs cannot be structured for calculation input
  • No special formatting is required beyond what is already standard HCLLP practice — the system reads the rows as they are

9. Frequently Asked Questions

QuestionAnswer
If Stage 2 uses the same data as Stage 1, why do we train again? Stage 1 teaches the model about all frameworks at once — like a general education. Stage 2 is like a specialization. The model already knows the shared vocabulary; now it fine-tunes its understanding of how each specific framework's citations, thresholds, and judgment patterns differ. Training in isolation per framework (building on Stage 1) produces sharper results than mixing all frameworks in one pass would.
What happens if we label a workpaper as timeless when it should be time_sensitive? The workpaper gets more weight than it should. If it contains outdated thresholds, those thresholds could influence the model slightly more than intended. The citation verifier in the output pipeline will catch any outdated regulation codes — but incorrect labels reduce training efficiency. When in doubt, label conservatively: time_static is a safe middle ground.
Can the AI see actual client data when generating outputs? No. All client-identifying information — names, EINs, SSNs, PAN numbers, bank accounts — is automatically removed from every workpaper before it enters the training data or the knowledge base. What the AI sees are anonymized versions: [CLIENT_ENTITY], [EIN], [PAN], etc. The structure and methodology of the workpaper is preserved; the client identity is not.
When the AI pulls "past examples" during inference, is it pulling from our actual client workpapers? Yes — but only the anonymized, PII-scrubbed versions. The retrieved sections show audit procedures, findings, and conclusions with all client identifiers replaced. You will see the methodology and language of past work, not the client name or specific account details.
What if the AI retrieves a past example that is not actually relevant to my workpaper? You will be able to see which past sections it retrieved. If any are clearly not relevant, you can note this in your correction and the system will log it. Over time, the reranker improves at selecting genuinely relevant examples, partly because these corrections feed back into the DPO improvement cycles.
Does the AI learn from every correction a senior auditor makes? Corrections from senior auditors and partners are collected in the system. Every quarter, when enough corrections have accumulated (target: 300+ in the first cycle), the model is re-trained using those corrections as preference examples — teaching it what better outputs look like compared to what it originally produced. Junior auditor corrections are collected but reviewed before being used in training.
How do we know the AI is not making up regulation citations? Every regulation code the model generates is automatically checked against a master list of currently valid regulations (2 CFR 200 series, AU-C series, SA series). Any code that does not appear on the list is flagged with a warning badge on the output. The auditor sees exactly which citations are verified and which are not — and the output cannot be promoted from "AI Draft" to "Validated" if it contains unverified citations.
Can the AI make arithmetic mistakes — wrong materiality amounts, incorrect reconciliation totals? No — because the AI never does the arithmetic. All calculations (materiality, bank reconciliation, trial balance totals, ratios, variances, threshold comparisons) are done by the Python Calculation Engine before the AI model receives any input. The AI sees verified, pre-computed numbers and writes the analysis based on those facts. This is the same principle as a spreadsheet formula: the formula computes; the auditor interprets. The AI interprets; it does not compute.
Does the Calculation Engine run for all workpaper types or only some? Threshold checks and materiality run for every workpaper regardless of type — every query benefits from knowing what the applicable thresholds and materiality figures are. The workpaper-specific tools (bank reconciliation, trial balance, ratios, variance analysis) run only when the workpaper_type label in your engagement_labels.csv matches — that label is what tells the system which calculations are relevant for each workpaper. Qualitative workpapers like internal_control narratives and planning documents receive threshold and materiality facts but no numeric row computation.
